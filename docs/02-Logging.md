# 日志规范

> 定义 OctoTify 项目中日志的格式、级别、字段、输出和管理规范，确保系统可观测性和问题排查效率。

---

## 一、概述

日志是系统可观测性的核心组成部分。统一的日志规范有助于：

- 快速定位和排查问题
- 监控告警和异常检测
- 性能分析和优化
- 审计和合规要求

---

## 二、日志格式

### 2.1 结构化日志

生产环境必须输出 **JSON 格式** 的结构化日志，便于日志采集系统（如 ELK、Loki）解析和查询。

开发环境输出 **纯文本格式**，保持字段结构清晰，便于使用 `grep` 等工具快速定位。

### 2.2 核心字段

所有日志必须包含以下基础字段：

| 字段 | 类型 | 说明 | 示例 |
|------|------|------|------|
| `level` | string | 日志级别 | `info`, `warn`, `error`, `fatal` |
| `time` | int64 | Unix 毫秒时间戳 | `1714644600000` |
| `message` | string | 日志描述信息 | `来源创建成功` |

### 2.3 业务日志字段

HTTP 请求相关的业务日志应额外包含：

| 字段 | 类型 | 说明 | 示例 |
|------|------|------|------|
| `request_id` | string | 请求唯一标识 | `0196a3b2c4d50000a1b2c3d4e5f67890` |
| `method` | string | HTTP 方法 | `GET`, `POST` |
| `path` | string | 请求路径 | `/api/sources` |
| `status` | int | 响应状态码 | `200`, `401`, `500` |
| `latency` | string | 请求耗时 | `125µs`, `45ms` |

### 2.4 日志示例

**成功请求：**

```json
{
  "level": "info",
  "time": 1714644600000,
  "request_id": "0196a3b2c4d50000a1b2c3d4e5f67890",
  "method": "POST",
  "path": "/api/sources",
  "status": 200,
  "latency": "45ms",
  "message": "来源创建成功"
}
```

**错误请求（BizError 日志由 ErrorHandler 中间件在 ERROR 级别记录）：**

```json
{
  "level": "error",
  "time": 1714644601000,
  "request_id": "0196a3b2c4d50000a1b2c3d4e5f67891",
  "error_code": 110500,
  "msg": "来源名称不能为空",
  "internal": "name is required",
  "path": "/api/sources"
}
```

## 三、日志级别

### 3.1 级别定义

| 级别 | 说明 | 使用场景 |
|------|------|----------|
| `DEBUG` | 调试信息 | 开发环境详细调试，生产环境默认关闭 |
| `INFO` | 一般信息 | 请求入口、业务操作成功、关键状态变更 |
| `WARN` | 警告信息 | 非关键错误、降级处理、可恢复的异常 |
| `ERROR` | 错误信息 | 业务逻辑失败、第三方调用失败、数据库错误 |
| `FATAL` | 致命错误 | 系统无法继续运行，需要立即介入 |

### 3.2 使用规范

日志库应提供对应级别的日志输出方法，以下为各场景应使用的级别：

| 场景 | 级别 | 示例 |
|------|------|------|
| 请求完成 | INFO | `请求完成: GET /api/sources, status=200, latency=45ms` |
| 请求完成（含错误状态码） | INFO | `请求完成: POST /api/sources, status=200, latency=12ms` |
| 操作成功 | INFO | `来源创建成功: sourceId=1, name=xxx` |
| 关键状态变更 | INFO | `用户登录成功: userId=1, ip=127.0.0.1` |
| 业务逻辑失败 | ERROR | `创建来源失败: 来源名称不能为空` |
| 第三方调用失败 | ERROR | `微信推送失败: sourceId=1, error=timeout` |
| 数据库错误 | ERROR | `查询来源列表失败: userId=1, error=connection refused` |
| 业务拒绝（资源不存在、已删除、已停用等） | WARN | `来源不存在: sourceId=1, userId=100` |
| 非关键错误 | WARN | `请求未携带 X-Request-ID，已自动生成` |
| 降级处理 | WARN | `第三方服务超时，使用缓存数据` |

> **说明**：HTTP 请求完成日志统一使用 INFO 级别，不区分状态码。这样可以避免恶意请求（如大量 404/403 扫描）导致 ERROR 日志膨胀。错误请求的详细信息由 `ErrorHandler`、`CustomRecovery` 中间件在 ERROR 级别记录。

## 四、日志输出

### 4.1 输出目标

| 环境 | 推荐输出目标 | 说明 |
|------|-------------|------|
| 开发环境 | 控制台（stdout） | 彩色输出，便于本地调试 |
| 生产环境 | 文件 + stdout | 文件用于持久化，stdout 用于容器日志采集 |

### 4.2 日志文件

| 配置项 | 推荐值 | 说明 |
|--------|--------|------|
| 文件路径 | `/var/log/octotify/app.log` | 应用日志主文件（可根据部署环境调整） |
| 错误日志 | `/var/log/octotify/error.log` | 仅 ERROR 及以上级别 |
| 日志轮转 | **按天 + 按大小双重生效** | 按天轮转：文件名格式 `app-2026-05-02.log`；按大小：单文件超过 100MB 自动切割 |
| 保留天数 | 30 天 | 超过 30 天自动清理 |
| 单文件大小 | 100MB | 超过后自动切割，单文件不超过 100MB |

## 五、日志查询

### 5.1 命令行查询

```bash
# 按 Request ID 查询完整链路
grep "0196a3b2c4d50000a1b2c3d4e5f67890" /var/log/octotify/app.log

# 查询错误日志
grep '"level":"error"' /var/log/octotify/error.log

# 查询特定路径的请求
grep '/api/sources' /var/log/octotify/app.log

# 查询慢请求（latency > 1000ms）
grep -E '"latency":[1-9][0-9]{3,}' /var/log/octotify/app.log
```

### 5.2 日志系统查询

使用 ELK、Loki 等日志系统时，推荐查询语句：

```
# 查询特定 Request ID
request_id: "0196a3b2c4d50000a1b2c3d4e5f67890"

# 查询错误请求
level: error

# 查询慢请求
latency: >1000

# 查询特定用户操作
userId: 12345 AND path: /api/sources*
```

## 六、敏感信息处理

### 6.1 禁止记录的敏感信息

以下信息**严禁**出现在日志中：

| 类型 | 示例 |
|------|------|
| 密码 | 用户密码、API Key |
| Token | Access Token、Refresh Token、Source Token |
| 个人隐私 | 手机号、身份证号、邮箱（需脱敏） |
| 支付信息 | 银行卡号、CVV |

### 6.2 脱敏规则

对于必须记录但包含敏感信息的字段，需进行脱敏处理：

| 字段 | 脱敏规则 | 示例 |
|------|----------|------|
| 手机号 | 保留前3后4 | `138****5678` |
| 邮箱 | 保留前2和域名 | `ab***@example.com` |
| Token | 仅记录前8位 | `src0196****` |

## 七、日志与 Request ID 的关系

日志系统必须与 [Request ID 规范](./01-RequestID.md) 配合使用：

1. **所有业务日志必须包含 `request_id` 字段**
2. **请求 ID 通过上下文机制传递**，不得通过全局变量
3. **日志框架应自动从上下文中提取 Request ID**，无需手动传递

---

## 八、实施建议

1. **统一日志框架**：全项目使用同一个日志库
2. **中间件集成**：在 HTTP 中间件中自动记录请求入口/出口日志
3. **监控告警**：基于 ERROR 级别日志配置告警规则
4. **日志采样**：高并发场景下可对 INFO 级别日志进行采样（如 10%）
5. **性能要求**：日志库应具备低分配特性，避免 GC 压力影响服务延迟
