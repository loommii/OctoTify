# 请求 ID 规范

> 定义 OctoTify 项目中请求 ID 的生成、传递和使用规范，确保分布式系统中请求链路可追踪。

---

## 一、概述

请求 ID（Request ID）是用于在分布式系统中唯一标识和追踪单个请求的标识符。通过请求 ID，可以快速定位请求链路中的所有相关日志，便于问题排查、性能分析和审计。

---

## 二、请求 ID 生成规则

### 2.1 格式要求

| 属性 | 要求 |
|------|------|
| **格式** | UUID v7（无连字符版本） |
| **长度** | 固定 32 个字符 |
| **字符集** | 小写十六进制字符 `[0-9a-f]` |
| **示例** | `0196a3b2c4d50000a1b2c3d4e5f67890` |

### 2.2 唯一性要求

UUID v7 结合时间戳和随机数，在同一毫秒内通过随机位保证唯一性，碰撞概率极低。

### 2.3 时间有序性

UUID v7 前 48 位为 Unix 毫秒时间戳，保证生成的 ID 单调递增，便于日志排序和数据库索引优化。

---

## 三、HTTP 请求传递方式

### 3.1 请求 Header

| 字段名 | 说明 | 必填 |
|--------|------|------|
| `X-Request-ID` | 请求唯一标识 | 否（建议客户端传递） |

### 3.2 请求示例

```
GET /api/application/list
X-Request-ID: 0196a3b2c4d50000a1b2c3d4e5f67890
Authorization: Bearer <access_token>
```

### 3.3 响应 Header

服务器必须在所有响应的 Header 中返回请求 ID，以便客户端关联请求与响应。

```
HTTP/1.1 200 OK
X-Request-ID: 0196a3b2c4d50000a1b2c3d4e5f67890
Content-Type: application/json
```

---

## 四、服务器端处理要求

### 4.1 请求接收

1. 优先使用客户端传递的 `X-Request-ID`
2. 若客户端未传递，服务端必须自动生成
3. 请求 ID 必须在整个请求生命周期内保持不变

### 4.2 请求传递

1. 请求 ID 必须在请求链路中全程传递
2. 调用下游服务或第三方 API 时，必须携带原始请求 ID
3. 请求 ID 应通过上下文机制传递，不得通过全局变量

### 4.3 响应返回

所有 HTTP 响应（包括错误响应）的 Header 中必须包含 `X-Request-ID`。

---

## 五、与日志系统的关系

请求 ID 与 [日志规范](./02-Logging.md) 配合使用：

1. **所有业务日志必须包含 `request_id` 字段**
2. **日志框架应自动从上下文中提取 Request ID**，无需手动传递
3. 通过 Request ID 可以快速检索单个请求的完整日志链路

日志查询示例：

```bash
# 使用 grep 检索日志文件
grep "0196a3b2c4d50000a1b2c3d4e5f67890" /var/log/octotify/app.log

# 使用日志系统查询（如 ELK、Loki）
request_id: "0196a3b2c4d50000a1b2c3d4e5f67890"
```

## 六、异常情况处理

### 6.1 未接收到请求 ID

当客户端未在请求 Header 中携带 `X-Request-ID` 时：

1. 服务端必须自动生成新的请求 ID
2. 不影响请求的正常处理流程

### 6.2 请求 ID 格式不符合规范

当客户端传递的请求 ID 格式不符合本规范要求时：

**策略**：不校验格式，直接使用客户端传递的值，以最大化兼容性。

### 6.3 服务内部错误

当服务内部发生 panic 或其他异常时：

1. 请求 ID 保持不变
2. 错误日志必须携带请求 ID
3. 响应 Header 中仍需包含请求 ID

---

## 七、实施建议

1. **全局中间件**：将请求 ID 处理注册为最外层中间件，确保所有路由覆盖
2. **前端配合**：建议前端在发起请求时生成并携带 `X-Request-ID`，便于前后端联调排查
3. **监控告警**：在监控系统中将请求 ID 作为关联字段，便于追踪异常请求的完整链路
