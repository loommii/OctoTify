# API 多语言规范

> 定义 OctoTify 项目中 API 响应消息的多语言处理规范。

---

## 一、概述

API 响应消息的多语言由**后端**负责，根据 HTTP 请求头 `Accept-Language` 返回对应语言的消息。

---

## 二、语言协商机制

### 2.1 请求头

客户端通过 `Accept-Language` 请求头告知服务端语言偏好：

```
Accept-Language: zh-CN,zh;q=0.9,en;q=0.8
```

### 2.2 语言权重

`q` 参数表示权重，范围 `0` ~ `1`，默认值为 `1`。服务器按权重从高到低匹配支持的语言。

### 2.3 语言代码格式

使用 [BCP 47](https://www.rfc-editor.org/rfc/bcp/bcp47.txt) 语言标签，以下为参考格式示例：

| 代码 | 语言 | 项目支持 |
|------|------|---------|
| `zh-CN` | 简体中文（中国） | ✅ |
| `zh-TW` | 繁体中文（台湾） | — |
| `en` | 英文 | ✅ |
| `ja` | 日文 | — |

---

## 三、处理规则

### 3.1 匹配流程

1. 解析 `Accept-Language` 请求头
2. 按权重从高到低匹配服务端支持的语言
3. 若无匹配，回退到默认语言（中文 `zh-CN`）

### 3.2 响应示例

**请求：**

```
POST /api/sources
Accept-Language: en
Content-Type: application/json

{"name": ""}
```

**响应（英文）：**

```json
{
  "code": 110500,
  "msg": "Source name cannot be empty",
  "data": null
}
```

**响应（中文）：**

```json
{
  "code": 110500,
  "msg": "来源名称不能为空",
  "data": null
}
```

### 3.3 核心原则

1. **错误码不变**：`code` 字段始终不变，作为错误的唯一标识
2. **消息可变**：`msg` 字段根据语言返回对应翻译
3. **日志记录**：日志中记录错误码和默认语言消息，便于排查

---

## 四、支持的语言

| 语言 | 代码 | 默认 |
|------|------|------|
| 简体中文 | `zh-CN` | ✅ |
| 英文 | `en` | |

---

## 五、实施建议

1. **翻译文件管理**：使用 JSON/YAML 文件按语言组织翻译
2. **中间件处理**：在中间件层解析 `Accept-Language` 并注入上下文
3. **缺失翻译处理**：若某条消息缺少对应语言翻译，回退到默认语言
4. **测试覆盖**：每个 API 错误响应需测试所有支持的语言
